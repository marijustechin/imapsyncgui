# TASK-003 — Design and implement imapsync runtime adapter

Design and implement the privileged runtime layer responsible for locating and executing `imapsync`.

This task introduces real process execution.

Do not build the final migration UI yet.

## Goal

Create a small, testable adapter around `imapsync` that:

- resolves the executable safely;
- launches it without using a shell;
- passes migration arguments safely;
- streams process output;
- supports cancellation;
- returns a typed final result;
- does not leak credentials.

The renderer must not receive access to child processes, filesystem APIs, executable paths, or arbitrary command execution.

## Research requirement

Before implementing the runtime strategy, determine how `imapsync` can reliably be distributed and executed on the initial supported platform: macOS.

Prefer official upstream distribution/documentation.

Do not download or commit arbitrary third-party binaries.

Document:

- what form `imapsync` is distributed in;
- whether it is a standalone executable or requires additional runtime/dependencies;
- what must eventually be bundled with the application;
- any packaging or licensing constraints relevant to redistribution;
- development-time versus packaged-application executable resolution.

Record the chosen runtime strategy in `docs/decisions.md`.

If a fully bundled production runtime cannot reasonably be completed in this task, implement a deterministic development/test strategy and explicitly document what remains for packaging.

Do not silently assume that `imapsync` is a single portable binary.

## Runtime adapter

Create a dedicated runtime module in privileged main-process code.

The adapter must not depend on React or renderer code.

It must expose application-level operations rather than generic process execution.

Suggested conceptual operations:

- start migration;
- observe migration output;
- cancel migration;
- obtain completion result.

Exact internal interfaces are up to the implementation as long as the public application contract remains narrow.

## Process execution

Use Node.js child process execution safely.

Requirements:

- use `spawn()` or an equivalently safe argument-array API;
- do not use `exec()`;
- do not invoke through `sh`, `bash`, `zsh`, or another shell;
- do not construct a single command string;
- executable path and arguments must be passed separately;
- renderer input must never control the executable path;
- renderer input must never introduce arbitrary command-line flags.

Only explicitly supported `imapsync` arguments may be generated by the adapter.

## Credentials

Credentials remain transient sensitive data.

Passwords must:

- not be written to logs;
- not appear in application-generated errors;
- not appear in renderer-visible diagnostic output;
- not be stored on disk;
- not be added to migration history;
- not be exposed through generic process objects.

If `imapsync` requires credentials to be supplied using command-line arguments, investigate safer supported alternatives before implementing that approach.

If credentials ultimately must be present in process arguments because of upstream constraints, document the security implications explicitly before considering the task complete.

Do not weaken the existing security requirements silently.

## Migration arguments

Translate the existing `MigrationInput` contract into a controlled `imapsync` invocation.

Support only the requirements currently defined by the product.

Do not add advanced `imapsync` flags merely because they exist.

Argument generation must be isolated into a testable function.

Tests must verify that user-controlled values cannot become executable flags or shell syntax.

## Process lifecycle

Represent at minimum these states:

- starting;
- running;
- succeeded;
- failed;
- cancelled.

Only one migration process may be owned by one adapter instance at a time.

Starting another migration while one is active must return a defined error rather than spawning another process.

## Output

Capture stdout and stderr.

The adapter must be able to emit output incrementally.

Before output is exposed outside privileged code, apply credential-safe sanitization.

Do not attempt to build sophisticated parsing of every `imapsync` log message in this task.

Raw sanitized textual progress is sufficient.

## Cancellation

Implement cancellation of the running migration.

Cancellation must:

- target only the process created by the adapter;
- be idempotent;
- not execute arbitrary operating-system commands;
- result in a typed cancelled state.

Document any platform-specific limitations.

## IPC integration

Connect the existing IPC contract to the runtime adapter where appropriate.

`startMigration()` and `cancelMigration()` must no longer be placeholder implementations if the runtime can be executed in the current environment.

Do not expose:

- `spawn`;
- `ChildProcess`;
- executable paths;
- arbitrary IPC channels;
- generic command execution.

If streaming output requires a new preload operation or event subscription, extend the contract narrowly and document the change.

Do not expose raw `ipcRenderer`.

## Dependency injection / testability

The process-launching mechanism must be replaceable in tests.

Tests must not require a real mailbox migration.

Unit tests must be able to simulate:

- successful process completion;
- non-zero exit;
- process startup failure;
- streaming stdout;
- streaming stderr;
- cancellation;
- duplicate start attempts.

Avoid introducing a heavyweight dependency injection framework.

## Tests

Add tests covering at minimum:

- correct executable resolution strategy;
- deterministic argument generation;
- no shell execution;
- supported migration options only;
- successful process execution;
- non-zero process exit;
- startup failure;
- stdout streaming;
- stderr streaming;
- cancellation;
- repeated cancellation;
- rejection of concurrent migration;
- credentials do not appear in generated logs or errors;
- malicious-looking host/user values cannot inject additional arguments;
- renderer remains unable to invoke arbitrary commands.

Do not require internet access or live IMAP servers for automated tests.

## Documentation

Update:

- `docs/architecture.md`
- `docs/security.md`
- `docs/testing.md`
- `docs/decisions.md`

README should be updated if development setup now requires an `imapsync` runtime.

Clearly distinguish:

- development setup;

## Scope restrictions

Do not:

- build the final migration form;
- add styling libraries;
- add Redux/Zustand or other global state management;
- add migration history;
- persist credentials;
- implement multiple simultaneous migrations;
- implement batch mailbox migration;
- implement automatic updates;
- add Windows or Linux support;
- add OAuth;
- add advanced `imapsync` configuration UI;
- weaken Electron sandboxing.

Do not solve future packaging problems with speculative abstractions.

## Verification

Run:

`pnpm verify`

All checks must pass.

If additional deterministic runtime verification is introduced, include it in `pnpm verify` only if it does not depend on external IMAP servers or network access.

## Acceptance criteria

- a dedicated `imapsync` runtime adapter exists;
- the executable resolution strategy is documented;
- actual process execution never uses a shell;
- invocation arguments are generated from an explicit allowlist;
- arbitrary command/flag injection is prevented;
- migration process lifecycle is typed;
- stdout/stderr can be consumed incrementally;
- cancellation works;
- concurrent execution is rejected;
- credentials are not persisted or emitted in application logs/errors;
- runtime behavior is testable without real IMAP servers;
- security boundary tests remain green;
- runtime/distribution decision is documented in an ADR;
- no final migration UI has been implemented;
- `pnpm verify` succeeds.
